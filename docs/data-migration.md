# Pinloom 데이터 이전 제안

상태: **설계 초안, 이전 미실행** · 2026-11-05

Runwick은 자체 저장소를 사용한다. 권장하는 첫 경로는 Pinloom의 일관된 스냅샷을 읽고 Runwick의 별도 데이터 영역에 가져오는 방식이다. 두 앱이 같은 SQLite 파일을 동시에 수정하는 방식은 제안하지 않는다.

## 데이터별 경로

| 원본 | 현재 export 포함 여부 | Runwick에서의 처리 제안 |
| --- | --- | --- |
| 프로젝트·세션·메시지 | DB JSON v2에 포함 | 원본 ID·시각·provider 정보·출처를 보존 |
| 메시지 핀·프로젝트 즐겨찾기 | 포함 | 메시지 관계와 pin 시각 보존 |
| 프로젝트 그룹·정렬·추가 설정 | 그룹 ID만 포함, 그룹 레코드 등 누락 | DB snapshot 어댑터로 보완하고 프로젝트 경로 재매핑 |
| provider 재개 ID | 포함 | 기록 열람 가능 여부와 CLI 재개 가능 여부를 별도로 표시 |
| provider 원본 transcript·수집 cursor | DB JSON만으로 불충분 | 별도 조사·수집. Runwick cursor는 독립적으로 생성 |
| 위키 Markdown | wiki-only 백업 또는 위키 디렉터리 | frontmatter, 수동 영역, 링크, 적용 프로젝트 보존 |
| 프로젝트 타임라인 Markdown | DB JSON·wiki-only에 없음 | 별도 디렉터리를 가져오고 날짜·프로젝트 관계 보존 |
| 세션별 타임라인·인수인계 캐시 | DB JSON에 없음 | 관련 DB 테이블을 별도로 매핑 |
| 환경변수 | DB JSON에 없음 | 키·설명·범위를 먼저 제시, 비밀값은 별도 저장 경로로 이전 |
| 프로젝트 메모·Teams·설정·템플릿 | DB JSON에 없음 | 목록과 의미를 조사한 뒤 지원·보존·제외 여부 보고 |
| 첨부 파일·이미지 | 파일 묶음으로 포함하지 않음 | 참조 경로와 파일 목록·크기·해시를 검증 |
| 임베딩·검색 인덱스 | DB JSON에 없음 | 재생성 가능한 파생 데이터로 분류; 가져오기 직후 자동 대량 작업 금지 |

확인 근거와 소스 버전은 [Pinloom 검토](research/pinloom.md)에 있다. 아직 실제 데이터의 건수·용량·누락률은 측정하지 않았다.

## 권장 절차

1. **읽기 전용 목록 확인:** schema 버전, 테이블·파일 종류, 건수·용량, 경로 매핑 후보를 확인한다. 비밀값과 대화 본문을 로그에 출력하지 않는다.
2. **일관된 snapshot 확보:** 실행 중 SQLite는 SQLite backup API 등 일관성을 보장하는 방식으로 확보한다. WAL 모드의 본체 파일만 복사해 완전한 백업이라고 간주하지 않는다. Markdown·첨부 파일은 목록과 해시를 함께 기록한다.
3. **시험 가져오기:** 별도 Runwick 데이터 디렉터리에서 수행하고 source namespace와 원본 ID를 저장한다. 같은 snapshot을 다시 가져와도 중복 생성되지 않도록 한다.
4. **검증 보고:** 종류별 원본·가져온 건수, 누락 파일, 관계 오류, 경로 재매핑, 지원하지 않는 필드를 표시한다. 지원하지 않는 내용은 조용히 버리지 않는다.
5. **사용 전환:** 사용자가 확인한 데이터만 활성 저장소로 선택한다. Pinloom은 계속 사용할 수 있고, 원본 기록은 변경하지 않는다.

실패한 배치는 활성 데이터로 노출하지 않는다. 자동화된 가져오기 테스트는 합성 데이터로 작성하고, 개인 대화·키·위키를 테스트 fixture로 커밋하지 않는다.

## 보존과 재개의 차이

- 대화 기록을 가져왔다는 것은 과거 내용을 읽고 검색할 수 있다는 뜻이다.
- CLI 재개는 해당 provider의 로컬 기록·실행 옵션·작업 디렉터리 등 추가 조건이 필요하다.
- 살아 있는 실행을 인수하는 것은 또 다른 기능이다. Pinloom의 실행 중 프로세스를 가져오는 기능은 현재 범위로 정하지 않았다.
- AI 요약은 파생 결과로 저장하고 원문을 대체하지 않는다. 원문에 없는 결정이나 작업 연결은 사실처럼 확정하지 않는다.

## 이전 완료 판정 제안

데이터 종류마다 지원·미지원·추가 확인 상태가 표시되고, 원본과 가져온 기록의 건수·관계·첨부 해시가 맞아야 한다. 같은 snapshot의 재실행은 중복을 만들지 않아야 한다. Runwick의 가져오기를 중단하거나 사용하지 않아도 기존 Pinloom 실행과 데이터에 영향이 없어야 한다.

실제 가져오기 도구 구현 전에는 지원할 Pinloom schema 버전, 첨부 저장 경로, 비밀값 저장 방식, 증분 이전 정책을 먼저 확정한다.
