# 세션에서 자연스럽게 확장되는 협업

상태: **추천 설계 · 사용자 검토 전 · 미구현** · 2026-11-05

관련 요구: RW-07~10, RW-13~14, RW-16. 선택지와 소스 근거는 [협업 구조 비교](research/collaboration-models.md), 전체 제품 경계는 [제품 기획](product-spec.md)을 따른다.

## 1. 기본 경험

사용자는 기존 CLI에 “로그인 오류 고쳐줘. 필요하면 Codex에게 검토도 맡겨”라고 말한다. 그 CLI가 필요성을 판단하고 다른 실행을 호출한다. 팀을 만들거나 ‘협업 모드’로 전환할 필요가 없다. AI가 혼자 끝내는 편이 낫다고 판단하면 추가 에이전트를 띄우지 않는다.

Runwick은 현재 세션 옆에 `협업 2 · 확인 필요 1`처럼 요약을 보여준다. 펼치면 맡긴 내용·작업자·도구·폴더·상태·결과를 볼 수 있다. 작업자는 먼저 미리보기로 열고 원하면 탭에 유지한다. 위임과 반환은 CLI에도 전달되며 Runwick 기록에는 별도 ID로 남는다.

사용자가 직접 역할을 만들고 싶으면 ‘작업 방식 저장’을 이용한다. ‘구현 + 검토’ 같은 조합은 재사용 가능한 힌트이며 반드시 그 수의 세션을 띄우는 고정 조직이 아니다. 팀 멤버 등록이나 한 팀에만 소속되는 조건은 두지 않는다.

## 2. 사용자의 자율성 선택

**추천 기본 방향은 허용한 범위 안에서 AI가 구성·진행하고 사용자가 개입하는 방식이다. 아직 이 세부 정책은 확정되지 않았다.** 다음 선택은 매 작업마다 나타나는 마법사가 아니라 설정과 실행 상세에 둔다.

| 선택 | 동작 |
| --- | --- |
| 필요할 때 협업 허용 / 추천 | 현재 요청과 허용된 프로젝트·도구·자원 범위 안에서 위임·재사용·순서 변경 |
| 구성 확인 후 진행 | 새로운 위임 구성을 보여주고 승인 후 실행. 같은 구성의 후속 턴은 반복 승인하지 않음 |
| 직접 선택 | 사용자가 작업자를 직접 시작하거나 선택. AI가 새로운 Runwick 작업자를 자동 생성하지 않음 |

이 설정은 Runwick을 통한 협업의 범위다. provider의 도구 권한·인증·명령 승인 설정을 몰래 바꾸지 않는다. CLI가 자체적으로 실행하는 내장 subagent에는 그 CLI의 정책이 적용된다. 표시 가능한 범위와 제어 가능한 범위를 구분한다.

공통 환경변수와 달리 ‘이번 작업의 목표·허용 경로·동시 실행 한도’는 작업 조건이다. 별도의 프로젝트별/실행별 환경변수 프로필을 추가한다는 뜻이 아니다. UI에서 환경과 작업 조건을 다른 위치에 둔다.

기본 접근 범위는 현재 프로젝트다. 사용자가 명시한 다른 프로젝트 또는 설정에서 허용한 프로젝트는 반복 확인 없이 연결할 수 있다. 프로젝트 목록에 등록되어 있다는 사실만으로 모든 프로젝트의 기록·파일을 모든 에이전트에 자동 제공하지 않는다. 범위 확대가 필요하면 필요한 대상과 이유를 묻는다.

## 3. AI와 실행 기반의 역할

| AI가 판단할 것 | 실행 기반이 보장할 것 |
| --- | --- |
| 일을 나눌 필요, 역할·도구 선택, 순서·병렬화 | 실제 지원 기능과 설치 상태, 자원 예약, 생성 결과 |
| 읽을 문맥, 완료 조건, 결과 해석 | 원문/파일/결과 ID, 출처·버전, 요청과 응답의 연결 |
| 작업자 재사용·재위임·수정 요청 | 입력 직렬화, 사람 제어권, 전송 확인, 중복 방지 |
| 검토 방식과 다음 작업 | 프로세스/요청/검증 상태 구분, 실패·복구·중지 |

Runwick의 CLI/API는 같은 코어 계약을 사용한다. AI가 현재 버전의 설명·지원 기능을 한 번 읽고 필요한 명령을 조회할 수 있게 한다. MCP 제공 여부는 어댑터 구현 선택이며 **MCP 팀 선언을 해야만 모든 기능이 열리는 구조로 만들지 않는다**. 앱도 같은 계약을 사용해 상태가 다르게 보이지 않게 한다.

개념상 필요한 연산은 실행 시작·조회·메시지 전송·상태 기다리기·결과 등록·기록 검색·작업 공간 분리·중지다. 정확한 명령 이름과 schema는 기술 설계에서 정한다. 터미널에 문자열을 붙여 넣는 것만으로 전달 성공을 확정하지 않는다.

## 4. 관계 모델

| 관계 | 규칙 |
| --- | --- |
| 프로젝트 → 공간 → 세션 | 확정된 탐색 구조. 각 세션은 현재 작업 공간을 명확히 가짐 |
| 세션 → 실행 | 살아 있는 실행과 종료된 과거 실행. 새로고침은 같은 세션의 새 실행일 수 있음 |
| 위임 요청 → 작업자 세션 → 시도 | 하나의 배정 ID로 전달/시작/결과 연결. 재시도는 새 시도 ID |
| 협업 내역 → 관련 요청/세션/공간 | 최초 위임 시 자동 묶음. 여러 프로젝트를 연결할 수 있음 |
| 할 일 → 선행 할 일/결과 | AI가 명시할 때만 의존 관계 등록. 순환 의존은 거부하고 원인 반환 |
| 생성한 부모 → 자식 실행 | 실행 출처·종료 범위. 작업 의존 그래프 전체와 같지 않음 |
| 결과 → 파일/원문/검증 | 결과를 만든 시도와 대상 revision/파일 해시·시각을 연결 |

작업 제목은 CLI가 제공한 제목이나 요청의 짧은 발췌를 쓴다. 제목 생성만을 위한 별도 LLM 호출은 하지 않는다. 상태·단계도 실제 보고된 것만 표시한다. 긴 문맥에 대해 정확히 몇 % 진행됐는지 모르면 숫자 대신 현재 행동과 마지막 보고 시각을 보여준다.

## 5. 위임 한 번의 계약

1. **준비:** 발신 세션, 현재 요청, 대상 공간, 지시, 필요한 권한·기능을 확인한다. 기존 작업자를 쓰면 현재 입력권·실행 상태를 확인한다.
2. **예약:** 요청/시도 ID와 중복 방지 키를 영속 저장한 뒤 실행 슬롯과 필요한 쓰기 범위를 예약한다. 같은 키로 재요청되면 기존 결과/상태를 돌려준다.
3. **생성:** 선택한 CLI를 실제 폴더·설정 버전으로 시작한다. 설치/인증/신뢰 대기/부팅 실패를 구별한다. 첫 지시가 전달되지 않으면 이를 표시한다.
4. **전달:** provider의 구조화된 인터페이스가 검증된 경우 이를 사용한다. 터미널 전달 경로는 readiness·현재 요청·사람 입력 여부를 확인한다. 상태가 불명확하면 전송 대기 또는 사용자에게 해당 터미널을 보여준다.
5. **진행:** 실행 이벤트와 대화 원문을 독립 수집한다. 긴 대기 호출이 만료돼도 실제 실행 중이면 요청 핸들을 유지한다. 상태 확인 만료로 같은 작업자를 새로 만들지 않는다.
6. **결과:** 작업자가 보고한 답변/파일/검증을 해당 시도에 연결한다. 기록 수집 지연은 ‘결과 수집 중’으로 표시하고 빈 답변을 성공으로 반환하지 않는다.
7. **반환:** 대표 CLI에 출처가 있는 결과를 전달한다. 사람이 입력 중이거나 승인 대기이면 안전한 경계까지 대기한다. 사용자 지시와 에이전트의 결과 보고를 구별한다.

전달 직후 연결이 끊겨 실제 수신 여부를 모르면 `전달 확인 필요`다. 런타임이 접수한 요청은 중복 생성하지 않지만, provider가 실행한 모든 외부 부작용에 대해 exactly-once를 보장한다고 주장하지 않는다. 조회·원문·실행 ID로 확인한 뒤 재전송한다.

## 6. 재사용·직접 개입

- 같은 작업자에게 후속 일을 줄 수 있다. 이전 작업이 진행 중이면 기본은 대기열에 넣기이며, 새 요청이 이전 작업을 자동 취소하지 않는다.
- 사용자가 직접 작업자와 대화하면 해당 세션에 ‘직접 조작 중’을 표시하고 자동 전송을 보류한다. 다시 맡기기를 누르면 현재 시도·남은 지시를 확인해 반환한다.
- 승인/질문 응답은 현재 실행과 요청 ID에 연결한다. 요청이 끝났거나 다른 turn으로 바뀌면 오래된 승인 버튼을 사용하지 못한다.
- 요청 ID를 제공하지 않는 CLI는 Runwick의 일반 승인 버튼으로 대신 누르지 않고 해당 CLI 화면으로 이동한다.
- 다른 협업이 기존 세션을 재사용하려면 입력권을 예약한다. 과거 결과를 읽는 것은 가능하지만 두 대표가 동시에 같은 CLI에 지시하지 않는다.
- 대표 교체는 지원되는 경우 인계 자료를 새 세션에 전달하는 별도 행동이다. 도구를 바꾸었다고 provider 대화 자체가 그대로 이전됐다고 표시하지 않는다.

## 7. 작업 공간·병렬 변경·통합

| 상황 | 기본 처리 |
| --- | --- |
| 읽기·설명·단일 순차 변경 | 현재 공간 사용 |
| 변경이 끝난 상태에 대한 검토 | 대상 revision/파일 스냅샷 고정 후 읽기. 현재 작업 공간이 변하면 검토 기준을 표시 |
| 독립적인 코드 변경을 병렬 진행 | 별도 worktree 공간을 제안. 허용된 ‘분리해서 작업’ 범위 안에서 생성 |
| 같은 폴더에서 병렬 편집 | 자동 기본값으로 삼지 않음. 명시한 파일 책임이 겹치면 대기/분리. 공유 파일의 변경 가능성도 표시 |
| Git이 아닌 폴더 | 순차 변경과 읽기 협업. 자동 복제나 유사 worktree를 몰래 만들지 않음 |
| 서로 다른 저장소 협업 | 각 공간에서 작업, 결과 연결. 통합 완료를 단일 Git merge로 표현하지 않음 |

자동 분리는 사용자가 ‘필요할 때 분리 허용’을 선택한 작업 범위 안에서만 수행한다. 그 외에는 CLI에 설명과 함께 제안하고 사용자가 ‘분리해서 작업’을 선택한다. 이는 모든 새 세션에 worktree를 만드는 정책이 아니다.

worktree 시작 시 출발 branch/revision, 미커밋 변경의 포함 여부, 실제 경로를 보여준다. 기본은 선택한 커밋에서 시작이며 현재 dirty 파일을 몰래 옮기거나 stash하지 않는다. 미커밋 작업을 포함하려면 별도 snapshot/patch로 범위를 확인한다. `.env` 복사·의존성 설치·외부 서버 시작은 worktree 생성에 암묵적으로 포함하지 않는다. 프로젝트에 사용자가 지정한 준비 명령이 있으면 내용을 보여주고 그 실행 정책을 따른다.

통합은 대상 branch와 비교 범위를 정해 준비한다. 변경 목록·검증 기준 revision·충돌·남은 항목을 보여준다. 로컬 통합, 커밋, push/PR/배포는 각각의 작업이다. 사용자가 CLI에서 이미 지시한 범위는 반복 승인하지 않되, 단순 위임 요청만으로 원격 반영까지 승인했다고 보지 않는다.

검증 뒤 파일이 바뀌면 기존 테스트 결과는 ‘이전 버전 기준’으로 바뀐다. 병합 충돌은 해당 공간에 보존하고 사용자가 해결/AI에게 맡기기/보류를 선택한다. 결과 확인과 worktree 정리는 분리하며, 미커밋·미푸시·실행 중 작업을 숨긴 채 폴더를 제거하지 않는다.

## 8. 상태 모델과 표시

| 축 | 상태 예시 | 주의점 |
| --- | --- | --- |
| 실행 | 시작 중, 연결됨, 종료, 연결 끊김, 상태 미확인 | 프로세스 생존과 AI의 작업 진행은 별개 |
| 시도 | 대기, 전달 확인 필요, 진행, 입력 필요, 결과 수집, 응답 완료, 실패, 중단 | 단순 대기 시간 만료는 실패 아님 |
| 할 일 | 준비, 선행 작업 대기, 진행, 결과 있음, 수정 필요, 완료, 중단 | 구조화된 할 일이 있을 때만 노출 |
| 검증 | 없음, 실행 중, 통과, 실패, 이전 버전 기준 | ‘AI가 완료라고 말함’과 별개 |
| 사용자 확인 | 답변 필요, 승인 필요, 새 결과, 확인함 | 읽었다고 검증 통과로 바뀌지 않음 |

대표 세션의 응답이 끝나도 자식이 실행 중이면 `응답 완료 · 협업 2개 진행`처럼 함께 표시한다. 배지는 숨긴 자식·다른 공간의 연결 실행도 같은 기준으로 집계한다. 동일 항목을 전체 활동과 세션 상세에 다르게 계산하지 않는다.

관심 우선순위는 `답변/승인 필요 → 복구 필요 → 새 결과 → 실행 중 → 대기`를 추천한다. 목록을 보고 있는 동안 상태 변경으로 행이 갑자기 이동하지 않도록 위치를 잠시 유지하고, 상태 텍스트는 즉시 갱신한다.

## 9. 자원·비용·재시도

프로토타입 추천값은 **Runwick 자동 배정의 활성 슬롯 예산 4개, 그중 자동 분석 최대 1개**다. 검증된 어댑터에서 관측한 대표 CLI의 활성 턴도 여유 슬롯 계산에 포함하며, 대기 중인 CLI 프로세스의 메모리는 별도 측정한다. 사용자 요청이 우선이고 새 자동 분석은 여유 슬롯이 있을 때만 시작한다. 숫자는 제품의 영구 상한이 아니며 설정에서 변경하고 실제 성능 측정 후 기본값을 확정한다.

이는 **새 Runwick 위임/자동 작업의 배정 기준이며, 컴퓨터 전체나 이미 열린 CLI의 직접 입력을 차단하는 상한이 아니다**. 사용자가 다섯 번째 CLI에 직접 입력하면 원래 CLI 동작을 유지하고, 관측한 초과 실행 수를 표시하며 새로운 자동 배정을 보류한다. UI 명칭은 ‘자동 배정 한도’로 하고 실제 관측 실행 수와 별도로 표시한다. 내부 subagent·외부 셸 실행처럼 관측/제어할 수 없는 실행은 제외 범위를 명시한다. 정확한 활성 상태를 모르는 관리 실행은 예약을 유지해 보수적으로 계산한다.

대표가 자식 결과를 기다리는 동안 자신의 활성 연산 슬롯을 계속 점유해 교착을 만들지 않도록 대기 상태와 실행 슬롯을 구분한다. 대기/계산 재개를 신뢰할 수 있는 어댑터에서만 슬롯을 반환·재예약한다. 이를 확인할 수 없으면 예약을 유지하고 해당 요청은 ‘실행 한도 확인 필요’로 보류해 기존 작업 재사용·순차 실행·사용자 한도 변경으로 풀게 한다. 전달 성공을 확인하기 전 기존 예약을 재사용하지 않는다.

- 시간·비용 한도가 있으면 시작 전에 실행 상세에 보이고 AI도 조회할 수 있다. 비용 측정이 안 되는 도구는 정확한 비용 차단 기능을 제공하는 척하지 않는다.
- 슬롯 부족은 `대기 · 실행 한도`로 표시한다. AI는 기존 세션 재사용·순차 처리·축소를 선택할 수 있다. 한도를 몰래 늘리지 않는다.
- 기본적으로 **실행이 시작되지 않았음이 확인된 일시적 연결 실패**만 제한적으로 자동 재시도한다. 프로토타입 후보는 최대 2회다. 전달 불확실·결과 품질 실패·사용자 중단은 자동 재전송하지 않는다.
- AI가 결과를 보완하려는 경우 동일 실패의 무한 수정을 막기 위해 시도 횟수·마지막 문제·시간을 공개한다. 공통 2회 수정 후 무조건 폐기 같은 고정 품질 게이트는 두지 않는다. 남은 한도와 사용자 요청에 맞게 보완·초안 제출·질문을 선택한다.
- 사용자 요청의 협업은 배터리에서도 실행한다. 자동 위키·임베딩에는 별도의 opt-in/전원 정책을 적용한다.

## 10. 멈춤·종료·복구

| 행동/사건 | 실행 처리 | 기록·다음 행동 |
| --- | --- | --- |
| 창 닫기/작업자 미리보기 닫기 | 실행 유지 | 현재 위치 보존, 메뉴 막대 활동 수 |
| 새 배정 보류 | 해당 협업의 미전달 대기열과 새 dispatch 정지. 이미 전달·시작한 턴은 계속 | 결과 저장, 대기 요청 유지, ‘배정 재개’ 표시 |
| 배정 재개 | 대기열의 취소 여부·입력권·의존 결과·경로·설정/권한을 재확인 후 전달 | 유효한 동일 요청 ID 유지. 전제가 바뀌었으면 재검토 필요 표시 |
| 현재 응답 중단 | 대상 시도 interrupt, 확인될 때까지 ‘중단 요청 중’ | 기존 출력/파일 보존. 후속 배정 보류 |
| 협업 중단 | 연결된 관리 시도와 후속 배정 중단. 별도 독립 실행은 제외 | 영향 목록·중단 결과. 실패한 종료도 표시 |
| 대표의 응답 완료 | 자식 자동 종료 없음 | 자식 진행 상태 계속 표시 |
| 대표 프로세스 예기치 않은 종료 | 새 배정 보류. 이미 작업 중인 자식은 현재 배정의 결과까지 수집하고 후속 자동 지시 금지 | 대표 재개 후 결과 인계, 또는 사용자가 자식 계속 사용 |
| UI/Core 재시작 | 실제 실행 생존 확인 후 연결. 존재를 확인하지 못한 실행은 중복 spawn 금지 | 저장된 요청/시도/결과로 대조 |
| OS 재부팅 | 실행 상실 표시. 임의 명령 재실행 없음 | 사용자가 재개할 세션/협업을 선택 |
| 세션 새로고침 | 해당 세션 배정 잠금, 현재 응답 종료 후 적용 또는 사용자 interrupt | 같은 대화 ID·논리 세션 보존. 실행 세대 변경 |

대표의 생명주기와 자식의 자동 종료를 무조건 묶지 않는 것이 추천안이다. 사용자가 명시적으로 협업 전체를 멈출 때는 종료 범위를 한 번에 지정한다. 예상치 못한 대표 종료에서는 자식에게 신규 지시를 보내지 않으며 완료한 결과를 잃지 않는다. 미지원 provider가 현재 턴 뒤 자율 작업을 계속하는 경우 중단을 요청하고 확인하지 못하면 `제어 확인 필요`로 남긴다.

보류는 전달 경계에서 원자적으로 판정한다. 이미 전달한 턴을 ‘아직 대기 중’이라고 표시하지 않는다. 보류 중 도착한 결과는 저장하고 화면에 알리지만, 대표에게 새 턴을 시작시키는 자동 입력은 배정 재개까지 기다린다. 이미 실행 중인 도구 호출의 응답은 기존 턴에 반환될 수 있으므로 ‘새 배정 보류’를 전체 실행 정지라고 설명하지 않는다. 사용자가 취소한 시도는 배정 재개로 되살리지 않는다. UI/Core 재시작 후에도 보류 상태를 유지한다.

복구·새로고침은 `실행 세대 + 요청/시도 ID`를 대조한다. 이전 실행에서 늦게 온 완료 이벤트가 새 시도를 완료시키면 안 된다. 재개 후에도 이미 반영한 결과는 중복 전달하지 않는다. 공유 daemon 변경이 무관한 세션을 중단시키는 경로는 사용하지 않는다. 정확한 대화 재개가 불가능하면 기존 실행을 먼저 종료하지 않는다.

## 11. 지원 수준과 준비 조건

| 수준 | 제공 경험 | 제한 표시 |
| --- | --- | --- |
| 일반 터미널 | 실행·연결·입출력·종료 | 대화 원문/진행/재개 미지원 가능 |
| 기록 연동 CLI | 위 기능 + 기록·핀·검색·지원 시 동일 대화 재개 | 마지막 수집 시각, 재개 조건 |
| 협업 연동 CLI | 위 기능 + 검증된 전달/결과/중단/상태 | 지원하지 않는 승인·자식 제어는 원래 CLI로 연결 |
| provider 내부 subagent | provider가 실제 노출한 정보만 표시 | Runwick 관리 작업자와 다른 표식, 미지원 제어 비활성화 |

CLI 업데이트로 특정 기능이 깨져도 터미널·기록 열람을 가능한 범위에서 유지한다. 오래된 어댑터는 지원 상태와 복구 안내를 보여주며 임의 키 입력으로 우회하지 않는다. 설치한 실제 CLI 버전으로 검증 매트릭스를 유지한다.

## 12. 설계 완료 조건

사용자가 팀을 선언하지 않은 채 한 세션에서 시작해 위임·결과 확인·개입·실패 복구·다음 날 이어하기까지 수행할 수 있어야 한다. 원문 검색·핀은 협업 기능을 쓰지 않아도 동일하게 작동해야 한다. 이 조건을 [사용 흐름](user-flows.md)의 F03~F07, F11~F13과 [화면 명세](ui-spec.md)의 S02~S06, S11~S12로 검증한다.
