# Runwick 전체 제품 기획

상태: **상세 설계 초안 · 사용자 검토용 · 구현 전** · 2026-11-05

사용자가 확정한 요구사항은 [결정 기록](decisions.md)이 기준이다. 이 문서의 상세 정책·화면·기본값은 이를 구체화한 추천안이며 별도 승인을 받았다는 뜻이 아니다. 전체 제품을 먼저 설계하고 구현 순서를 따로 정한다. 협업·위키·타임라인을 ‘첫 버전 밖’이라는 이유로 기획에서 제외하지 않는다.

## 1. 제품의 중심

**기존 CLI로 바로 일하고, 필요하면 여러 AI로 확장하며, 그 과정과 맥락을 잃지 않는 개인 작업실.**

사용자는 프로젝트를 열고 Claude·Codex·셸을 실행한다. 팀 생성, 목표 등록, 역할 편성, worktree 생성은 시작 조건이 아니다. 협업이 필요하면 현재 CLI 에이전트가 Runwick의 실행 수단을 사용한다. Runwick은 실행을 지속하고, 누가 무엇을 하고 있는지 보여주며, 대화·핀·결정·결과를 다음 작업에 연결한다.

AI의 역할 분해와 판단은 현재 사용하는 에이전트가 맡는다. 모든 입력을 다시 읽는 별도 상주 LLM 플래너를 기본으로 두지 않는다. 상태 갱신·기록·검색은 AI 호출 없이 작동한다.

## 2. 사용자에게 보이는 단위

| 단위 | 의미 | 생성 시점·책임 |
| --- | --- | --- |
| 프로젝트 | 제품·저장소·폴더, 위키·타임라인·즐겨찾기의 기준 | 폴더 열기. Git이 없어도 사용 |
| 작업 공간 | 실제 폴더와 열린 세션·문서 배치 | 기본 공간 자동 생성. 필요할 때 분리 |
| 세션 | 계속 이어갈 CLI 대화 또는 일반 터미널 | 사용자가 시작하거나 에이전트가 위임 |
| 실행 | 세션을 현재 구동하는 프로세스 | 재개·새로고침마다 달라질 수 있음 |
| 협업 내역 | 위임 요청, 참여 세션, 결과의 연결 | 첫 위임 시 자동 기록. 별도 조직 선언 없음 |
| 할 일 | 에이전트가 명시한 목표·범위·완료 조건·의존 관계 | 필요할 때만 생성. 단순 대화에는 강제하지 않음 |
| 시도 | 한 요청을 실제 실행한 이력 | 재시도 시 새 항목. 이전 결과 보존 |
| 역할/작업 방식 | 재사용 가능한 지시문·선호 도구·절차 | 선택적으로 저장. 실제 세션이나 팀 소속과 다름 |
| 기록·핀·지식 | 원문, 보관한 발췌, 위키·타임라인·이어하기 메모 | 실행 종료와 독립적으로 유지 |

탐색의 기본은 **프로젝트 → 작업 공간 → 세션**이다. 협업 내역은 여기에 붙는 관계이며 새로운 필수 상위 폴더가 아니다. 동일 세션은 여러 협업의 과거 결과와 연결할 수 있다. 현재 입력/실행의 배정은 충돌하지 않도록 직렬화한다. 여러 저장소의 협업도 허용하되 실제 파일은 각 세션의 작업 공간에 속한다.

## 4. 평소 작업 흐름

1. 앱을 열면 마지막 작업 공간을 복원한다. 새 사용자는 폴더 열기만으로 시작한다. 확인할 일이 있어도 현재 화면을 빼앗지 않고 배지와 활동 목록으로 알린다.
2. 중앙에서 CLI를 쓴다. 왼쪽에서 프로젝트·공간을 바꾸고 세션/파일 목록을 전환한다. 문서는 중앙 탭이나 분할로 연다.
3. 검색·핀·위키·타임라인·협업 상세는 필요할 때 연다. 단축 동작으로 열고 닫아도 입력 중인 CLI와 문서 편집은 유지한다.
4. CLI가 검토자나 다른 구현자를 부르면 대표 세션 아래에 작업자가 나타난다. 모든 작업자 탭을 자동으로 전면에 열지 않는다.
5. 답해야 할 일이 생기면 해당 실행의 현재 요청으로 이동한다. 작업자는 잠깐 보거나 정식 탭으로 유지할 수 있다.
6. 완료 뒤에도 실제 결과와 대화가 그대로 남는다. ‘작업 완료’만 적힌 빈 화면으로 대체하지 않는다.
7. 다음 날에는 최근 세션·핀·수동 이어하기 메모·선택한 AI 요약을 보고 살아 있는 실행에 연결하거나 같은 대화를 재개한다.

상세 협업 정책은 [협업 설계](orchestration.md)를 따른다. 기존 CLI의 내부 subagent와 Runwick이 실행한 다른 CLI는 표시와 제어 가능 범위를 구분한다.

## 5. 지식과 기록 정책

### 대화와 검색

- 터미널 scrollback과 구조화된 대화 저장을 분리한다. 원문 수집 상태·마지막 시각·미수집 범위를 표시한다.
- source namespace, provider conversation ID, 메시지 ID/원본 위치와 버전을 보존한다. 같은 텍스트가 있다는 이유만으로 메시지를 합치지 않는다.
- 빠른 첫 결과 뒤 추가 결과를 점진적으로 로딩한다. 한국어 문구·부분 일치·코드 기호를 검증한다. 재색인 시 이전 유효 색인을 계속 읽을 수 있게 한다.
- 핀은 본문 스냅샷과 출처를 함께 보관한다. 원본이 없어져도 발췌는 남으며 ‘원문 연결 불가’를 표시한다. 핀 해제와 원본 삭제는 별개다.
- 검색 결과 열기는 CLI 입력이나 스크롤을 조작하지 않는다. ‘기록 보기’와 ‘대화 재개’는 다른 버튼이다.

### 위키와 타임라인

- 위키에는 문서 제목·프로젝트·수정일·근거 세션·검토 상태를 표시한다. 직접 편집한 내용과 AI 변경 제안은 구분한다.
- 추천 기본값은 AI가 변경 초안을 저장하고 사용자가 diff를 보고 적용하는 방식이다. 자동 반영은 사용자가 선택한 AI 관리 영역에 한해 별도 허용하며 수동 영역은 보호한다.
- 상충하는 결정을 발견하면 새 결정으로 조용히 덮지 않고 출처와 충돌을 표시한다. 원문 없는 AI 추론은 추론으로 남긴다.
- 타임라인은 실제 세션/핀/변경 이벤트를 AI 없이 보여준다. AI 요약이 실패해도 빈 날짜로 보이지 않는다. Git 변경 감지는 저장소 상태 확인 정책을 따르며 매 프레임 스캔하지 않는다.
- 작업 인계에는 필요한 핀·위키 버전·파일 경로·결과만 선택해 전달한다. 모든 기록을 매번 프롬프트에 넣지 않는다. 경로/링크 복사와 짧은 인계 문서 내보내기를 제공한다.
- 내보내기에는 원문/파생 결과의 구분과 출처를 포함한다. 환경변수 비밀값은 기록·인계·일반 백업에 포함하지 않는다.

### 여러 프로젝트의 협업 기록

대화·파일·개별 결과는 실제 세션이 속한 공간/프로젝트에 귀속한다. 핀도 원문 세션의 프로젝트에 속하며, 원문 메시지를 식별하지 못한 터미널 발췌는 채취한 세션의 프로젝트에 속한다. 다른 프로젝트에서 핀을 참고할 때는 참조를 연결하고 원본을 중복 생성하지 않는다. 협업 내역은 원래 요청 프로젝트에서 다른 프로젝트의 결과를 참조하며 원문을 복제하지 않는다. 타임라인에는 각 프로젝트에서 발생한 사건과 협업 참조를 표시한다. 프로젝트별 자동 위키/요약은 해당 프로젝트에 귀속된 허용 자료만 입력으로 사용한다. 협업 연결만으로 다른 프로젝트의 모든 기록이 자동 분석 대상이 되지 않는다. 필요한 타 프로젝트 자료는 인계 범위로 명시해서 연결한다.

## 6. 자동 작업과 자원 정책

| 종류 | 시작 조건 | 배터리 | 중지·재개 |
| --- | --- | --- | --- |
| 대화 수집·키워드 색인 | 원문 변경 | 계속 처리하되 묶음·상한 적용 | 실패 지점부터 재시도, 중복 수집 금지 |
| 사용자가 CLI에 맡긴 일과 그 위임 | 사용자 요청 및 허용된 협업 범위 | 실행 가능 | 사용자가 해당 일/시도 중단, 필요 시 이어가기 |
| 자동 위키·요약·임베딩 | 프로젝트 opt-in, 변경분 축적, idle | 새 분석 보류 | 새 배정 중지. 실행 중 전원 변경 시 현재 최소 단위 결과를 저장한 뒤 다음 단위 보류 |
| 사용자가 누른 ‘지금 정리’ | 명시적 요청 | 실행 가능 | 자동 실행 정책과 별도 표시 |

동시 실행·저장/출력 한도·자동 재시도 수는 화면에서 확인 가능해야 한다. 추천 프로토타입 값은 [협업 설계](orchestration.md)의 자원 정책에 기록하고 성능 검증 뒤 확정한다. 무조건 12분 뒤 전체 작업을 실패시키는 공통 제한은 두지 않는다. 응답 없음·보고 없음·시간 한도 도달을 구별하고 실행 중단 여부와 남은 결과를 표시한다.

자원 한도는 Runwick 자동 배정에 적용하는 기준과 실제 관측 실행 수를 구별한다. 사용자가 열린 CLI에 직접 입력하거나 provider가 내부 작업을 실행하는 것까지 모두 차단할 수 있다고 보장하지 않는다. 관측 가능한 직접 실행도 새 자동 배정의 여유 계산에는 반영한다.

비용은 provider가 제공하는 실제 사용량, 추정, 미지원으로 구분한다. 구독 CLI를 API 가격으로 환산해 실제 청구액처럼 표시하지 않는다. 지원되지 않는 비용 측정은 프로세스 수·시간 한도 등 관측 가능한 제어로 보완한다.

## 7. 설정·저장·복구 경계

- Runwick 환경변수는 공통 설정 하나다. 프로젝트별/실행별 환경 프로필을 추가하지 않는다. `.env`는 해당 도구가 읽는 방식에 맡긴다.
- MCP는 provider가 실제 사용하는 설정의 위치·범위·연결 상태를 보여준다. provider의 프로젝트 MCP 설정을 Runwick 프로젝트 환경 프로필과 혼동하지 않는다. 설정 저장과 실행에 반영됨을 구분한다.
- 비밀값은 OS 자격증명 저장소 등 별도 보안 저장소에 두고 일반 설정에는 참조만 보관하는 안을 우선 검증한다. 표시/복사/내보내기는 각각 명시적 사용자 행동이다.
- Runwick은 Pinloom과 DB를 공유해 쓰지 않는다. 가져오기는 활성 데이터와 분리한 배치에서 검증 후 노출한다.
- 앱 내부 기록 삭제·worktree 제거·백업 복원은 대상과 영향이 명확한 별도 행동이다. 세션 보관/탭 닫기/기록 삭제를 한 버튼으로 묶지 않는다.
- 저장 실패 시 ‘저장됨’을 표시하지 않는다. 원문 수집이 멈춰도 현재 터미널을 즉시 종료하지 않으며 오류와 복구 수단을 노출한다.

## 8. 구현을 나눌 책임 경계

아래는 제품 동작을 지탱할 설계 제안이며 라이브러리·DB DDL 확정이 아니다.

| 구성 | 책임 | 포함하지 않는 책임 |
| --- | --- | --- |
| 네이티브 GUI | 탐색·터미널 표시·문서·활동·사용자 입력 | 창이 닫혔다고 작업 종료, 자체 LLM 계획 판단 |
| 실행 관리자/PTY 소유자 | 실행 수명·입력 직렬화·연결·중지·자원 예약 | AI 답변의 정답 판정 |
| provider 어댑터 | 지원 기능, ID·원문·상태·재개·설정 반영 계약 | 미지원 기능을 추정해 지원으로 표시 |
| 협업 기록·배정 | 요청/시도/결과/관계·중복 방지·대기·현재 제어권 | 매 턴 LLM 재계획, 고정 팀 인원 강제 |
| 기록·검색 저장소 | 원문·핀·메모·색인·출처·버전 | 원문을 AI 요약으로 대체 |
| 자동 작업 실행기 | opt-in·전원·idle·변경분·재시도·상태 | 숨은 분석 실행 |
| 파일·Git 연동 | 선택 공간의 파일·diff·분리·통합 준비 | 무관한 작업 트리 변경, 사용자 편집 덮어쓰기 |
| 가져오기·백업 | 일관된 snapshot·매핑·검증·복구 | Pinloom 프로세스나 활성 DB 수정 |

기술 검증은 터미널/IME, 기록 수집, 재개/새로고침, 실행 생명주기, 협업 전달, 데이터 이전으로 나눈다. 상세 구현 계획도 이 경계별로 작성한다. 하나의 거대한 구현 계획으로 모든 기능을 동시에 바꾸지 않는다.

## 9. UI 디자인 착수 기준과 미확정 항목

이 초안은 화면 구조·행동·상태·예외 흐름을 정해 UI 시안을 만들기 위한 기준이다. 실제 구현에 들어가기 전에는 사용자 검토와 기술 실험이 필요하다.

| 항목 | 현재 추천 | 확정 시점 |
| --- | --- | --- |
| 협업 UX | 세션에서 자연스럽게 확장, 팀 생성 없음 | 사용자 기획 검토 |
| AI 자율 범위 | 설정한 범위 안에서 위임·진행, 필요할 때 개입 | 사용자 기획 검토. 아직 새 정책의 승인으로 취급하지 않음 |
| UI 구조 | 중앙 CLI/문서, 좌측 탐색, 우측 필요 시 상세, 전역 활동 | UI 시안 비교 |
| 네이티브 GUI/터미널 기술 | Rust 네이티브라는 방향만 확정 | IME·색상·출력·배터리·유지보수 실험 |
| 기록 저장 형식 | 검색 가능한 DB + 사람이 다룰 문서 파일 후보 | 크기·원문 식별·백업 실험 |
| OS/배포/자동 업데이트 | macOS에서 먼저 검증, 출시 지원 범위 별도 | 패키징·서명·업데이트 복구 설계 |
| 원격 실행·기기 전환 | 2026-11-06 제품 방향 합의. 각 기기 실행 유지, 같은 사이드바에서 공간 전환 | [원격 검토](research/orca-remote.md)의 상세 연결/기록 계약과 2기기 실험 |
| 임의 코드 mod | 현재 필수 요구 아님 | 실제 개인화 요구와 안전한 적용/복구 설계 |

원격 실행은 2026-11-06 사용자 동의로 제품 방향에 포함했다. 로컬에서 바로 시작하고, 원격 기기를 등록하면 같은 사이드바에서 해당 작업 공간을 선택한다. 각 기기의 실행 유지와 GUI 연결을 분리한다. [원격 검토](research/orca-remote.md)의 실행 위치·파일/기록 소유권·설정 적용·연결 복구 상세안은 추가 설계 대상으로 남는다. 출시 순서나 연결 기술을 확정한 것은 아니다.

SaaS 협업, 전체 IDE, 디자인/기획 전용 에이전트, 앱을 실시간으로 바꾸는 임의 코드 mod는 이번 전체 제품 기준의 필수 기능으로 넣지 않는다. 요청한 CLI·협업·기록·위키·타임라인·환경·편집 경험은 독립적으로 완결되도록 설계한다.
